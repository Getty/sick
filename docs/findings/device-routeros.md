# MikroTik RouterOS through the acme.sh hook `routeros`

Question: does SICK's `acmesh` target, with the deploy hook `routeros` of
acme.sh, put a certificate from SICK on a RouterOS router so that its
www-ssl service presents it - and what does it take on the router?

**Answer: yes**, against a real RouterOS (CHR 7.24.5 in qemu), with the
policies `ssh,ftp,read,write`. No change to SICK was needed.

Card k53 (part of P7, k17). Run on 2026-10-11 on agent-lab by
`t/e2e/device-routeros.sh` (both parts, `ALL PASSED`, 46 PASS lines; the CHR
part three times in a row, 69-71 s each).

first name `router.example.internal`, `host` 127.0.0.1 and the published
port of the router's 443. `ROUTER_OS_SSH_CMD`/`_SCP_CMD`: `-F /dev/null -p

StrictHostKeyChecking=yes -o UserKnownHostsFile=<known_hosts made at test
time>`. `ROUTER_OS_ADDITIONAL_SERVICES` sets api-ssl. Every container carries
`sick=1` and `sick.e2e=device-routeros`, is removed by those labels, at the
start (an interrupted run) and at the end; no volume, no network, ports on
127.0.0.1. Checked after the run: no container, no volume with those labels.

### Part 1: recording stand-in

An sshd container whose deploy key has a forced command
(`t/e2e/routeros-standin.sh`). It records uploads (name, size, mode - never
content) and commands byte for byte, answers like RouterOS 7, and presents
on a TLS port what the commands "imported". **This proves what our side
sends, not what RouterOS does with it**; part 2 does that.

Recorded for one deployment, in this order:

```
upload sftp router.example.internal.key 1704 600
upload sftp router.example.internal.cer 1241 644      <- fullchain.cer
exec 1   :do {/system script remove "LECertDeploy-<name>" } on-error={ }; /system script add
         name="LECertDeploy-<name>" owner=sick comment="generated by routeros deploy script in acme.sh"
         source="/certificate remove [ find name=<name>.cer_0 ];\n ... cer_1, cer_2, cer_3 ...
         \ndelay 1;\n/certificate import file-name=\"<name>.cer\" passphrase=\"\";
         \n/certificate import file-name=\"<name>.key\" passphrase=\"\";\ndelay 1;
         \n:do {/file remove <name>.cer; } on-error={ }\n:do {/file remove <name>.key; } on-error={ }
         \ndelay 2;\n/ip service set www-ssl certificate=<name>.cer_0;
         \n/ip service set api-ssl certificate=<name>.cer_0;\n"
exec 2   /system script run "LECertDeploy-<name>"
exec 3   /system script remove "LECertDeploy-<name>"
```

(The script checks command 1 byte for byte, one line, with a trailing
newline.) The hook parses no output; it looks only at the exit code of each
ssh/scp. scp of OpenSSH 10 uses the SFTP protocol; the key keeps mode 0600
on the way. Asserted besides: second run `unchanged` and nothing sent; an
unknown host key fails the device before anything is uploaded; a script run
with exit 1 fails the device with the router's message; a script run that
imports nothing and exits 0 gives acme.sh `Success` and SICK `verification
failed`, and leaves `<name>.key` on the "router" until the next good run.

### Part 2: RouterOS CHR in qemu (TCG) - tried, works

- **Boot:** the REST API answered 31 s after `docker run` (TCG, no KVM),
  every time.
- **Setup without a console:** the fresh CHR has `admin` without password
  and the `www` service (80) with the REST API on. Through it: group `sick`
  with exactly `ssh,ftp,read,write` (the REST `set` of `policy` only adds -
  the others must be named with `!`), user `sick` with a random password
  nobody uses, `/user/ssh-keys add` of the ed25519 deploy key, www-ssl and
  api-ssl enabled. Host key out of band: `/ip/ssh/export-host-key`, read
  `<prefix>_rsa_pub.pem`, both exported files (the export writes the private
  half too) removed, `ssh-keygen -i -m PKCS8` into known_hosts. The CHR's
  host key is RSA (`host-key-type: rsa`).
- **Real hook through SICK:** `sick check` says `missing` (www-ssl enabled
  without a certificate accepts TCP and closes); `sick run` renews in about
  8 s; the fingerprint on 443 equals SICK's issued one and RouterOS's
  `/certificate` entry `router.example.internal.cer_0` (with private key);
  www-ssl and api-ssl use `cer_0`; no file and no script left on the router.
- Second run `unchanged`; `--force` renews and `cer_0` is the new
  certificate - the only one; the old one is gone.
- Unknown host key: the device fails, the router is unchanged.
- `/certificate import` of a file that is not there, over ssh: the error is
  printed, **exit code 0**. A syntax error (`/foo`) is exit 1; `:error` is 0.
- Group without `read`: RouterOS answers the script creation with
  `interrupted` and exit 1, acme.sh fails, www-ssl keeps the previous
  certificate. Both files stay in `/file`, the key included. (One
  exploratory run before the script existed saw creation succeed, the run do
  nothing, acme.sh `Success` and SICK `verification failed`; not reproduced
  in three scripted runs.)
- Exploratory, by hand, all with `-v` output: `ssh,write` fails at the upload
  (`Received disconnect`); `ssh,ftp,read` fails at the upload
  (`dest open ...: Permission denied`). So: **`ssh,ftp,read,write`, each
  needed.**
- No `PRIVATE KEY` and no line of the deploy key in SICK's output, its
  records or the router's log (which records the whole script source - file
  and certificate names only).

## Recipe facts for the handbook

**Rights, and how to keep them small.** Group with `ssh,ftp,read,write` and
the rest explicitly off (`contrib/devices/routeros/sick-user.rsc`). MikroTik's
documentation (help.mikrotik.com, "User", last updated 2026-04-15, read
2026-10-11): `ssh` "log in remotely via secure shell", `ftp` "full rights to
log in remotely via FTP", read/write/delete files and transfer them, "should
be combined with the read and write policies"; `read` "read access to the
router's configuration"; `write` "write access to the router's
configuration, except for user management". `write` is the big one: it is
most of the router. What keeps it small: a group of its own, `address=` on
the user (only the SICK host), the key in SICK's file only, no password
login (`password-authentication=yes-if-no-key`, the 7.24.5 default - by its
name, passwords only for users without a key; not tested). Not needed: `sensitive`, `policy`,
`password`, `api`, `rest-api`. RouterOS's log shows the hook's script added
with `policy=""` (observed, not looked up).

**Where the secret lives.** The deploy key: a file on the SICK host, named
in `ROUTER_OS_SSH_CMD`/`_SCP_CMD` - a path, not a secret, in the device list;
the hook has no password setting at all. known_hosts: a file next to it. The
certificate's key: briefly in SICK's private temp home (0700/0600), then on
the router as a file `<name>.key` until the script imports and removes it,
then inside RouterOS's certificate store. After a failed deployment it may
stay in `/file` (readable for every user with `ftp`).

**What RouterOS restarts.** Nothing visible: `/ip service set www-ssl
certificate=<name>.cer_0` and www-ssl presents the new certificate at the
next connection; no reboot, no service disable/enable. The hook does not
enable www-ssl - that is setup. On 7.24.5 the CHR also has a `reverse-proxy`
service on 443; with www-ssl enabled, www-ssl answered.

**How `sick check` sees success.** `host`/`port` of the device at www-ssl
(443 unless moved). This matters more than usual: RouterOS answers failures
at run time with exit code 0, so `acme.sh: Success` does not mean imported.
The fingerprint on the port is the only reliable signal, and SICK compares
it after every deployment.

**How to get back.** The hook removes `<name>.cer_0` .. `_3` before it
imports: after a deployment the previous SICK certificate is gone from
`/certificate`. Other certificates (one made on the router, an older one
under another name) stay; `/ip service set www-ssl certificate=<other>`
returns to one. Otherwise: run SICK again.

**Further facts.**
- With `ROUTER_OS_SSH_CMD`/`_SCP_CMD` set, `ROUTER_OS_PORT` is ignored: the
  port goes into those commands (`ssh -p`, `scp -P`).
- The hook word-splits those variables: no spaces in the paths in them.
- ed25519 deploy keys work on 7.24.5.
- RouterOS's own log records each ssh login and the full script source.

## Not tried

- A physical router; RouterOS 6 (the hook's naming comment says 6.32-6.41.3;
  7.24.5 still names `<file>_0`).
- A chain with an intermediate (step-ca): the leaf should be `cer_0`, the
  intermediate `cer_1`; whether www-ssl sends the intermediate was not seen.
- An EC key on the router.
- What www-ssl presents in the ~4 s between the script's `certificate
  remove` and `service set`.
- `scp -O` (legacy protocol) - the stand-in handles it, nothing used it.
- A deployment with a non-default ssh port on the router side (the test's
  non-22 port was the published port of the container).
