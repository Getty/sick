# OS trust matrix: the generated install and remove scripts, run as they are

Question (karr k37, part of P4/k14): `sick trust` writes `trust-linux.sh` and
`trust-nss.sh` (and the macOS and Windows scripts). Run for real, as root, on
each Linux family: do they refuse without the right fingerprint and write
nothing, install only the root, make the system clients accept the CA and
refuse what they must refuse, remove what they installed, and do so a second
time without harm?

Run by `t/e2e/trust-os.sh` (read its header for the case list). The scripts
are generated by `perl -Ilib bin/sick -c <config> trust <dir>` against a
throwaway PKI made by `openssl` at run time (root R, an intermediate
name-constrained to `DNS:example.internal`, leaves and an unrelated root), and
run **without `SICK_TRUST_ROOT`**, as root, in one container per distribution.
Nothing is checked in; the PKI lives in a private temporary directory.

## Result

`ok` means every assertion of the step passed in that container (count in the
log). Clients per step: `curl`, `openssl s_client` (OpenSSL) and `gnutls-cli`
(GnuTLS), always with hostname checking; the NSS step uses `tstclnt`.

The first two runs had one FAIL, a script bug (below), since fixed; a third
run after the fix passed every step on all six distributions. Everything else
was identical on the two first complete runs (about four and a half minutes each, 80 assertions per
Debian-family and RHEL-family container).

### Reasons given by the clients

The negatives are refused for the right reason, not for a missing root: wrong
name, `hostname mismatch` (OpenSSL), `SSL: no alternative certificate subject
name matches` (curl), `The name in the certificate does not match the expected`
(GnuTLS); outside the constraint, `permitted subtree violation` (OpenSSL, curl)
and `The certificate chain violates the signer's constraints` (GnuTLS); unrelated
CA, `unable to get local issuer certificate` / `The certificate issuer is
unknown`. The unconstrained control (4k) is accepted in every container, so the
refusal of step 4 is the constraint's doing.

### What the scripts put where

- Debian, Ubuntu, Alpine: `/usr/local/share/ca-certificates/sick-root-<16 hex>.crt`,
  then `update-ca-certificates`. Exactly one file; the root is in
  `/etc/ssl/certs/ca-certificates.crt` afterwards and gone after `remove`.
- Fedora, Rocky: `/etc/pki/ca-trust/source/anchors/sick-root-<16 hex>.pem`,
  then `update-ca-trust extract`; the root is in
  `extracted/pem/tls-ca-bundle.pem` and gone after `remove`.
- Arch: `trust anchor --store`; the clients of the system accept at once
  (`trust anchor` refreshes the bundle itself here), `trust anchor --remove`
  takes it out again.
- **No script put the intermediate anywhere** in the system stores (step 5):
  the anchor directory holds one file, the generated bundle lacks the
  intermediate (checked by its base64 line), p11-kit lists no intermediate. And
  the service that sends its leaf alone (a switch) is **refused** by all
  three clients after the install: the intermediate is not secretly an anchor.
  For such a device the script says to use `ca_bundle.pem` as the program's own
  CA file, as the findings of trust-anchors.md recommend.
- A refused install writes nothing: a hash of the file names and contents of
  the anchor directories, `/etc/ssl/certs`, `/etc/pki`, `/etc/ca-certificates`
  is the same before and after the wrong, missing, mixed and malformed
  fingerprints. The script also prints the fingerprints it computed and which
  one matches or was not given.

### NSS (`trust-nss.sh`)

Into a fresh database (`certutil -N --empty-password`): wrong fingerprint and
none: exit 1, no nickname written. Right fingerprint: `sick root <16 hex>` with
flags `C,,` and `sick intermediate <16 hex>` with flags `,,`. With `tstclnt`
(Debian, Ubuntu, Fedora, Rocky): the good service accepted; the service that
sends its leaf alone **accepted** too (the `,,` intermediate helps build the
chain without being an anchor; matches 5d of trust-anchors.md); wrong name
refused (`SSL_ERROR_BAD_CERT_DOMAIN`); unrelated CA refused
(`SEC_ERROR_UNKNOWN_ISSUER`); the out-of-constraint leaf refused
(`SEC_ERROR_CERT_NOT_IN_NAME_SPACE` on Rocky's NSS 3.124, plain
`SEC_ERROR_UNKNOWN_ISSUER` on the newer NSS of Debian, Ubuntu and Fedora; the
control through the unconstrained intermediate is accepted, so it is the
constraint); after `remove` refused, the database holds nothing of ours, and a
second `remove` exits 0 with "not installed". On Alpine and Arch the NSS
package has `certutil` but no `tstclnt`/`vfychain`: there only the database is
checked (refusals, nicknames, flags, remove, remove again), not what a client
says.

## Script bug found, and fixed

**`trust-linux.sh remove` on p11-kit systems (Arch) is not idempotent in what
it says.** In `lib/SICK/Trust/Scripts.pm`, `_linux`, the remove loop (around
line 511):

```sh
if trust anchor --remove "$TMP/root_$i.pem" >/dev/null 2>&1; then
  say "removed: root certificate $i, a p11-kit anchor"
  removed=1
else
  say "not installed: ..."
```

`trust anchor --remove` exits 0 when nothing matches, so the `else` is never
reached. A second `remove` on Arch (observed, p11-kit 0.26.5) prints
`removed: root certificate 1, a p11-kit anchor` and `Done: the system store no
longer trusts ...` although nothing was installed. Exit code 0 and the store
are right; the message is wrong and, with the Debian and Fedora families
saying "not installed", the three families disagree. The fix is to check
`trust list` for the certificate (for example by its label or `--filter`)
before removing.

**Fixed** on 2026-10-10: the p11-kit branch compares `trust list
--filter=ca-anchors` before and after `trust anchor --remove` and reports
"removed" only when the list changed (that list holds every anchor whatever
its purpose; `trust extract` would miss a root limited to other purposes).
`t/50-trust.t` has a regression test with a fake `trust` that, like p11-kit
0.26.5, exits 0 without a match. The rerun of this script: step 7 ok on Arch,
71 PASS, 0 FAIL.

Smaller observation, not a defect of the script: Debian's
`update-ca-certificates` prints `rehash: warning: skipping ca-certificates.crt`
on every call; harmless.

## What follows for the page

- The Linux script does what the page says on all six families: refuses
  without the fingerprint (and with a mismatching or a malformed one) and
  writes nothing, installs the root alone, removes it again, and the
  intermediate is never an anchor in a system store.
- A service that presents its leaf alone is **refused** on every system
  store after the script ran. This is intended, and the page keeps pointing at
  `ca_bundle.pem` or at a service that sends its chain. Firefox/NSS is the one
  place where the same device works (`,,` intermediate).
- Package prerequisites: Debian, Ubuntu and Alpine need `ca-certificates` for
  `update-ca-certificates` (the minimal images lack it; the script says so),
  Rocky and Fedora `ca-certificates`, Arch `p11-kit`. NSS scripts need
  `libnss3-tools` / `nss-tools` / `nss`.

## Not tried

- **`trust-macos.sh` and `trust-windows.ps1` behaviour.** The macOS script
  passed `sh -n` in every container. The PowerShell script was parsed with the
  PowerShell parser in `mcr.microsoft.com/powershell` (7.4.2, `--rm`): no
  errors. Neither was run: no macOS keychain, no Windows certificate store.
- Firefox itself and Chrome (only `tstclnt` over the NSS database); the profile
  directory of a running Firefox, `policies.json`.
- Java, Python, Node and Go after the Linux script: see trust-runtimes.md.
- Other families (openSUSE, Gentoo, NixOS), older releases than listed, Debian
  with p11-kit anchors, a read-only root file system, `sudo` instead of root,
  a second root in the same install (`additional_roots`), an install with the
  Windows line-ending copy of the script.
- A tampered script or a tampered page: the fingerprint check is proved to
  stop a mismatching root, not an attacker who also controls the fingerprint
  channel.
